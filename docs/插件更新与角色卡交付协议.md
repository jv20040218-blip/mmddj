# 明日方舟剧情模块：插件更新与角色卡交付协议

协议版本：1.0；生效日期：2026-11-15。

本协议属于项目开发文档，约束后续 AI、开发者和交付流程。用户的当次明确要求优先；未经用户要求，不得把远程更新交付退回为本地文件交付。

## 一、最终交付标准

每次功能更新或修复，必须交付下面两项可直接使用的结果：

1. **可在现有插件内更新的远程插件链接**：已安装用户通过酒馆扩展管理中的检查更新／更新获得新版，无需手动复制文件或卸载重装；首次安装用户可以使用同一仓库链接。
2. **与该插件版本配套的新角色卡**：提供可下载的 PNG 直链，角色卡包含所需的基础世界书和运行脚本，按酒馆正常导入流程即可使用。

生成了本地目录、ZIP、源码或角色卡文件，不等于完成交付。它们可以用作备份，但不能代替已发布的插件链接和新角色卡直链。

## 二、插件地址与发布规则

- 当前正式安装仓库：`https://github.com/jv20040218-blip/mmddj`。
- 正式更新分支为 `main`。后续更新继续发布到原仓库、原更新分支，使现有安装保留更新来源。
- 每次交付新版本号，并建立对应的不可变 Git 标签，例如 `v1.3.0`。固定安装地址可以保持不变，但必须确认远程实际内容已更新。
- 可以另提供标签页、提交页或发布说明页作为“本次新版链接”；不得把 GitHub 的 `tree/标签` 页面冒充一定可用于酒馆安装的仓库地址。
- 不得为了给出不同的地址而每次另建一个仓库，让用户重新安装。用户未要求迁移时，保留插件身份、原更新来源及安装目录。
- 安装文件放在仓库根目录：`manifest.json`、`index.js`、`style.css` 和 `data/`。不能提交成外面再套一层交付文件夹，导致酒馆找不到清单。
- 插件版本号必须递增。清单、入口声明、发布记录应一致；不能只改 README 中的版本数字。

## 三、配套角色卡规则

- 每次发布提供与本次数据、脚本和世界书匹配的新卡。不能只更新插件数据而继续给出一张使用旧 UID 或旧脚本的卡。
- 默认提供**含配套基础世界书的完整插件版角色卡**。这里的完整是包含必要脚本与世界书，不把大体积剧情原文库重新塞进 PNG。
- “极简卡＋另行导入世界书”可以作为可选方案，不能在用户未要求时作为唯一方案，增加额外设置步骤。
- 卡文件使用带版本的稳定文件名，例如 `cards/ark-story-v1.3.0.png`；提供标签对应的下载直链，避免下载后悄然变成其他版本。
- 必须可从 PNG 中解出卡数据，核对角色版本、世界书绑定、脚本构建标识。不能把截图、预览网页、JSON 或指向旧卡的链接当作新卡。
- 世界书内容改变时采用可区分的新名称，并同步卡内绑定；不能要求用户先删掉同名旧书才能导入。卡中应带正确绑定，尽量减少导入后的手动选择。
- 旧卡可以留作回退，不要求用户删除旧卡、旧聊天或重新开始故事。

## 四、更新体验与兼容要求

普通用户的更新路径应保持为：

> 在原插件中更新 → 刷新页面 → 下载并导入本次配套新卡。

用户不得被要求手动覆盖插件文件夹、移动数据文件、修改源码、执行开发命令，或卸载插件后重新安装。卡片的正常导入不属于插件卸载重装。

- 保持从 `import.meta.url` 等实际安装位置解析数据地址，兼容原插件目录被命名为 `mmddj` 等情况，不把用户的绝对磁盘路径写进插件。
- 更新后必须重新取得新版本数据，不能因缓存继续加载旧数据。数据清单应提供版本、构建标识、字节数和 SHA-256。
- 卡、插件、世界书与数据的兼容关系要可检查。发现版本不匹配，应显示明确的更新提示，不能静默混用或假装成功。
- 保留稳定的剧情、节点、角色和状态标识；新增条目不得无故挤占已有世界书 UID。确需变更时提供程序迁移，不把恢复工作转嫁给用户。
- 聊天进度、完成记录、回忆作用域、人物状态、结束回执应能恢复。未可靠定位时提供续点选择，不自动猜测、更不清空聊天。
- 插件更新不应额外启动重复脚本实例。旧卡保留在角色列表中，不应要求先删除它才让新卡运行。
- 当前架构中，数据由插件提供，主要界面与运行逻辑仍在角色卡脚本中。因此本阶段必须配套交付新卡；未经授权，不以本协议为由擅自重构整个架构。

## 五、剧情与人物功能的交付底线

- 保留主线分块、支线按国家的多级目录，先预览后进入；点击展开一项时收起同级其他项。
- 上方分类标题固定为“主线、支线、其他”。主线采用“主线 → 1–8／9–14／15–17 → 每章”的三级可展开标题；支线采用“支线 → 国家 → 每章”。不以选择框替代每章标题，不把章节平铺到一级，也不在其他里重复已纳入的分章。无国家归属的篇目、人物专题和联动放入“其他”。
- 原始1–5合编素材对应的现有序章及1至5章分章原文，应归回第一块的逐章标题。合编入口保留为旧存档兼容，不重复展示；旧合编进度完结后仍能接第6章。
- 每次构建对当前主线／支线目录中的 JSON 逐文件核对。国家与专题归属必须由源文件夹路径重建，不能只改分组标题而沿用错误成员。新增文件未编译或旧入口失效时，构建须明确报错，不能静默发布缺项版本。
- 角色线标题读取明确的人物资料或素材焦点，不直接暴露内部节点代号、原始 ID 或把误解析的句子当人名。无明确人物的内容标为剧情片段；同一交汇场景的不同人物视角不能简单按重复场景删掉。
- 支持任意幕／段切换；略过的内容不补记为完成，模型判断不能成为唯一的推进途径。
- 状态栏持续给出时间、当前情况、同时事件或沿用的上一事件、下一步、出场人物及实际匹配的资料后缀。
- 支持确认当前段、末段结算、任意时刻保存退出、结束回执和结尾原文查看。单线结束与整篇全部线路完成分别记录。
- 进入、正常推进、手动切幕、退出回忆和恢复聊天时，重新判断同名人物的状态与来源档案；明确的场景／时期锚点优先。
- 用户已明确人物切换的含义是**实际关闭旧条目、打开对应正确条目并写入世界书**。生成时的临时投影可以辅助防止错态，不能替代实际开关；开场须等待写入并回读核对。切线串行化，退出恢复原开局或外层剧情；保留玩家选择的性别等身份，不能被默认状态覆盖。
- 原世界书重置按钮覆盖全部基础、剧情指导和来源人物条目，恢复开关及触发类型；先退出活动剧情并撤除当前注入，保留剧情进度。仅恢复旧基础条目不算完整重置。
- 日期不明继续写“暂无”。未明确标定的变化节点不编造日期或事实，补充资料的来源与未完成映射必须有记录。
- 剧情对白原文保留在可核对的数据文件中，不能悄然以梗概替代。玩家预览未来内容不等于给模型提前注入未来剧情。

## 六、开发与发布顺序

1. 在开发工程中完成当次明确要求，保留原素材和可回退版本。
2. 同步生成插件数据、新角色卡、世界书、构建记录与必要的存档迁移。
3. 执行与修改相关的测试和最终产物检查；已有通过且未受影响的检查无需无意义地反复运行。
4. 在原远程仓库的正式分支提交本版。不能覆盖不相关的用户修改；正常推送，不强制改写已发布历史。
5. 发布对应版本标签和带版本的新卡；更新 README 与发布记录中的安装、下载链接。
6. 从远程读取并检查正式分支和标签，核对版本、数据哈希和卡文件哈希。只有本地提交、没有成功推送，仍属未发布。
7. 交付正式插件安装／更新地址、配套新卡直链，以及必要的简短使用说明。

用户已经明确要求发布且现有仓库与权限足够时，直接完成，不反复要求确认同一发布动作。若确实缺少凭据或权限，明确说明具体阻塞；不得冒称远程已经更新，也不得索要用户不必提供的信息。

## 七、远程验收记录

每次发布记录至少包含：

| 字段 | 要求 |
| --- | --- |
| 正式仓库和分支 | 现有安装使用的更新来源 |
| 版本号、标签与提交 SHA | 能唯一定位本次发布 |
| 卡片下载地址 | 标签对应的 PNG 直链 |
| 卡片 SHA-256 与字节数 | 与本地验证的卡一致 |
| 数据版本、SHA-256 与字节数 | 与配套卡要求一致 |
| 世界书名称与条目数量 | 与卡内绑定及运行 UID 一致 |
| 测试结果 | 说明检查对象和真实通过结果 |
| 界面／宿主测试范围 | 区分本地页面、内存宿主与实际酒馆；不能混称 |
| 回退版本 | 可定位的旧标签与旧卡 |

能通过既有测试和哈希确定未变的原文数据，不为制造“已测试”的表述反复调用付费模型。未经当次授权，不新增付费模型测试成本。

## 八、最终回复模板

最终回复优先给出可用结果，保持简短：

> 已发布 vX.Y.Z。  
> 插件安装／更新：[仓库链接]  
> 新角色卡：[带版本 PNG 直链]  
> 已安装用户：在原插件内更新并刷新，再导入新卡；无需覆盖文件或卸载重装。  
> 验证：简述实际测试与远程核对结果。

不得把“需要用户手动覆盖文件才能生效”写成已满足本协议。存在未发布、未匹配的卡或必须手动迁移的问题时，应如实指出，继续完成能够自主处理的部分。

## 九、本次适用说明

本协议覆盖结束状态栏与来源人物档案版 1.3.0，以及此后的剧情模块更新。1.3.0 本地功能验证记录为 194 项测试、151 项交付检查及 21944 段原文比对通过；**远程是否发布必须另以实际推送与远程核对记录证明**，不以这组本地测试数字代替。

## 十、代理直接更新已授权酒馆服务器

用户要求代理代安装／更新时，代理完成服务器上的实际操作，不能再让用户下载、覆盖文件或卸载重装。服务器地址与凭据由授权会话或临时环境变量提供，不写入本协议、公共仓库、角色卡或发布日志。

1. **定位运行实例。** 从实际服务端口进程确认工作目录、数据用户及插件目录，不更新同机器上的备用副本。确认原插件的origin、当前提交、启用状态与同源副本数量。
2. **先构建并发布。** 新卡、插件数据与世界书配套，测试与哈希核验通过后，正常推送原仓库和新标签；记录精确提交与发布清单。
3. **通过SSH直传。** 外网下载慢时，用健康仓库生成Git差异bundle并通过SFTP上传。验证服务器具备基准提交、包的哈希及实际导出的引用；只fetch包里存在的引用，不请求未导出的标签。
4. **原插件原位快进。** 保留原目录和origin，使用`git fetch <bundle>`及`merge --ff-only`更新。保持工作区干净，使以后仍可在酒馆里更新；遇到不相关用户修改时保留并整合。
5. **确定真实目标并保存原卡元数据。** 核对当前实际头像标识；无浏览器条件时至少读取服务器保存的active_character并标注证据来源。使用包含尾号的完整文件名，不得写死“默认卡名.png”或凭显示名称判断。建立实际头像→卡版本→脚本构建/哈希→绑定书→书格式的对应记录；插件版本不能代替这组检查。用户指定其他目标时使用明确目标；无关角色或目标不明时不得猜测覆盖。导入前从该目标的角色API记录聊天指针、收藏并备份，不读取聊天正文。
6. **自动导入配套书和卡。** 使用已认证会话、Cookie与CSRF令牌调用酒馆自身接口。世界书按稳定UID导入并与新卡绑定；卡导入保留原头像文件名，避免给用户增加同用途重复卡。卡内 CharacterBook 的 `keys/secondary_keys/enabled` 与酒馆原生书的 `key/keysecondary/disable` 属于不同格式：不得仅把 entries 数组包装成 UID 字典后直接写入。使用构建产物 `data/base_worldbook.json`（`release.json` 中 `worldbook.schema=sillytavern_native`），并核对位置、顺序、递归、概率等字段；卡内标准 `enabled` 与原生 `disable` 必须一致。
7. **恢复最近聊天。** 卡导入可能重置`chat`。导入后通过`edit-attribute`恢复API先前返回的真实值，再从角色API读回核验。不能仅修改PNG某个块就认为恢复成功，`chara`与`ccv3`可能保留不同旧值。
8. **验证后删除旧重复插件。** 确认新版本可用后，仅清理已核实的同源旧重复安装目录，保留一份最新剧情插件；不影响其他插件和用户聊天。
9. **核验实际服务与实际目标。** 对第5步的同一头像核对卡版本、脚本哈希、实际绑定书及聊天指针，再检查HTTP插件版本、数据清单、单份安装和启用状态。读取该目标真正绑定的书，逐条验证原生字段并执行助手读取及开局回归；不能拿另一张新卡或另一本新书的通过数替代。具备浏览器条件时实点原先失败的开局；缺少该项须明确标注，不笼统称用户端全部正常。对map等重复错误采集本次调用目标和栈，区分读取与写回。详见 `更新指导_1.7.0开局map错误复发.md`。
10. **结束交付。** 清理本次上传临时文件，保存不含凭据的部署回执，并同步桌面既有的三项使用包。用户刷新酒馆即可使用，不需要再手动安装。

现有工程的逐步命令、真实安装路径、可复用脚本及已遇到的问题，见同目录的 `支线核对与补全交接_2026-11-16.md` 第6节。该交接文档列出的历史路径和版本需按本次发布参数化，不能盲目运行固定旧版本补救脚本。

## 十一、1.7.0复发补充：插件版本不代表当前卡已更新

本次插件为1.7.0、默认头像也为1.7.0，但服务器保存选中的尾号1头像仍为1.5.1，绑定格式错误的v4_1书。固定覆盖默认头像的部署方式已修正；实际选中卡已补正并保留其聊天和收藏，正确v5_0书未重置。

后续施工必须验证“**实际头像完整文件名 → 卡版本 → 卡内脚本哈希 → 实际绑定书 → 原生字段有效**”这条完整关系。遇到同名或带尾号的卡，用头像标识区分；不能仅验证插件版本、默认文件或临时验收书。页面未实点的验收须如实标注。

完整复盘、施工步骤与验收反例见[更新指导：1.7.0开局map错误复发](https://github.com/jv20040218-blip/mmddj/blob/main/docs/更新指导_1.7.0开局map错误复发.md)。
